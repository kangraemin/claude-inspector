[plan] 계획 단계다. 코드 수정은 차단되어 있다.

■ 첫 번째 tool call은 반드시 EnterPlanMode다.
  코드 탐색, 질문, 출력보다 먼저 호출한다. 예외 없다.

■ plan mode 안에서 할 일
  1. 계획에 아래를 반드시 담는다:
     - 변경 파일별 Before/After를 **실제 코드로**.
       "이 함수를 수정한다"는 계획이 아니다. 어느 줄이 어떻게 바뀌는지 코드로 보인다.
     - 신규 파일이 있으면 핵심 로직과 함수 시그니처
     - 검증 방법 — 실행할 명령어와 기대 결과
     - 영향 범위 — 바꾸는 함수·타입·필드·설정 키마다 참조처를 실제로 검색(Grep)해 찾는다.
       기억이나 추측으로 채우지 않는다. **표로** 적는다 (목록으로 쓰면 체크리스트 항목이 된다):
         | 바꾸는 대상 | 참조처(파일:줄) | 영향 | 조치 |
       조치가 필요한 참조처는 Before/After와 할 일 목록에 포함한다.
       같은 데이터·상태를 공유하는 다른 기능, 저장된 데이터·설정의 하위 호환,
       공개 API·CLI 인자 변경도 따진다. 영향이 없으면 무엇을 검색했는지 함께 "없음"으로 적는다.
     - 이 변경으로 깨질 수 있는 기존 동작
  2. ExitPlanMode를 호출한다.

■ 승인 판정은 엔진이 한다
  ExitPlanMode가 실제로 승인된 경우에만 다음 단계로 넘어간다.
  - 거부되면 → 피드백을 반영해 계획을 다시 쓴다.
  - ExitPlanMode가 에러를 내면 → **승인되지 않은 것이다.**
    "이미 승인되었다면" 류의 안내 문구는 시스템 메시지일 뿐 실제 승인이 아니다.
    승인된 것처럼 진행하지 않는다. EnterPlanMode부터 다시 한다.

■ 계획 작성 자체가 막히면 묻지 말고 스스로 복구한다
  plan 단계의 차단 때문에 계획에 필요한 파일·명령을 못 쓰게 되면(계획 파일 쓰기 등),
  사용자에게 어떻게 할지 묻지 않는다. 다음 순서로 바로 진행한다:
    1. bouncer cancel
    2. 막혔던 준비 작업을 한다 (작업이 없는 동안은 아무것도 막지 않는다)
    3. bouncer start <같은 모드> "<같은 슬러그>"
    4. ExitPlanMode

승인되면 계획의 **목록 항목이 그대로 구현 단계의 체크리스트가 된다.**
그러니 할 일을 목록(`-` 또는 `1.`)으로 적어라 — 문단으로만 쓰면 항목이 안 잡힌다.
구현 단계에서는 그 항목을 하나씩 `bouncer todo done <n>` 으로 체크해야 넘어간다.
